through git while keeping the human's operational effort small.\n\n## goal\n\na chat agent receives a stable identity once. master writes immutable jobs into its personal workspace. the human starts each future job by typing exactly `go` in the same bound agent chat. the agent retrieves the job itself and writes typed responses and evidence back for master verification.\n\nthe human does not transport job prompts, artifact lists or return instructions between chats.\n\n## project structure\n\n```text\nprojects/{projectslug}/\n├── agents/\n│   ├── index.json\n│   └── {agentid}/\n│       ├── identity.json\n│       ├── initialization.json\n│       ├── state.json\n│       ├── inbox/\n│       │   ├── index.json\n│       │   ├── {jobid}.json\n│       │   └── {jobid}.md\n│       ├── outbox/\n│       │   ├── index.json\n│       │   └── {jobid}/\n│       │       └── {responseid}.json\n│       ├── evidence/{jobid}/\n│       └── audit/{jobid}/\n└── master/\n    ├── jobs/{jobid}.json\n    ├── response-resolutions/{responseid}.json\n    ├── scheduler/state.json\n    └── status/\n        ├── project.json\n        ├── agents.json\n        ├── jobs.json\n        ├── responses.json\n        ├── reviews.json\n        └── blockers.json\n```\n\n## ownership\n\n### master-owned\n\n- agent registry and identities;\n- one-time initialization artifacts;\n- inbox indices and immutable job contracts;\n- human-readable job projections;\n- authoritative master job lifecycle;\n- response resolutions;\n- scheduler, lease and compact status projections.\n\n### agent-owned within the job authorization\n\n- its own runtime state;\n- typed response objects and response-index update;\n- job evidence and audit records;\n- product artifacts only in the explicitly assigned work repository, branch and paths.\n\nthese ownership rules are protocol limits. actual provider permissions remain authoritative. json cannot grant missing rights.\n\n## one-time chat initialization\n\nmaster generates an immutable initialization artifact containing:\n\n1. project and master identity;\n2. technical `agentid`;\n3. separate human-readable `displayname`;\n4. control repository;\n5. exact identity, state and inbox-index pointers;\n6. communication contract;\n7. fail-closed reidentification behavior.\n\nthe human pastes the generated prompt once into a new chat. the agent reads back and validates the referenced identity. future jobs use the same continued chat and need no new job prompt.\n\nif chat continuity or identity cannot be proven, the agent does not guess. it emits `reidentification_required` and directs the human back to master.\n\n## activation\n\na normal `chat_agent` begins work only after direct human input:\n\n```text\ngo\n```\n\nthe token is trimmed and may be case-insensitive, but additional job text is not allowed. the activation is bound once to the selected job and dispatch revision.\n\na git push, repository change, polling loop, scheduler decision, automation or host event does not activate a normal chat agent. the scheduler publishes a safe job as `waiting_human_go` and lists it for the human.\n\nservice agents, when supported, use a separate explicit activation contract. their semantics must not be silently applied to normal chat agents.\n\n## pointer-only job discovery\n\nafter `go`, the agent reads in order:\n\n1. pinned identity;\n2. own state;\n3. fixed personal `inbox/index.json`;\n4. selected immutable job;\n5. selected authoritative `master/jobs/{jobid}.json`;\n6. only inputs explicitly pinned by the job.\n\nthe normal flow forbids:\n\n- global repository search;\n- project-tree full scan;\n- reading other agents' inboxes;\n- unreferenced artifact discovery.\n\nthe inbox index is only a discoverability projection. job contract and master job state remain authoritative.\n\n## preflight before mutation\n\nthe agent verifies:\n\n- identity status and chat binding;\n- identity revision and exact assignment;\n- human-go evidence for the selected job;\n- job and projection blob identities;\n- active mandate;\n- role, skill, domain and technology compatibility;\n- immutable inputs;\n- dedicated product branch and allowed paths;\n- separate product and response write targets;\n- actual provider capabilities and rights;\n- active resource leases;\n- stop, pause and stale-reference conditions.\n\na failed preflight produces a typed blocker response before unauthorized product mutation.\n\n## typed responses\n\nevery job binds exact templates, schemas and paths for:\n\n- `job_result`\n- `job_error`\n- `clarification_request`\n- `capability_mismatch`\n- `improvement_proposal`\n\nthe response is immutable and tied to project, job, package, work item, agent, identity revision and observed job blob.\n\na later master resolution is a separate immutable artifact. it may acknowledge the response, document a decision or reference a superseding job. it never rewrites the original response.\n\n## minimal agent chat\n\ndetailed work, checks, errors, conflicts and evidence are git artifacts. the agent chat emits only one-line statuses:\n\n- `ready`\n- `started`\n- `submitted`\n- `blocked`\n- `reidentification_required`\n\nthe agent does not conduct domain discussion or scope negotiation with the human. master owns those interactions.\n\n## authoritative lifecycle\n\n```text\nprepared\n→ waiting_human_go\n→ go_observed\n→ claimed\n→ running\n→ response_submitted\n→ verified\n→ accepted\n→ integrated\n```\n\npossible branches include `blocked`, `rejected`, `rework_ready`, `canceled` and `superseded`.\n\n`response_submitted` is not verification. `verified` is not acceptance. `accepted` is not integration.\n\n## rework\n\na substantial task, role, skill or authority change creates a new job. historical job ids are never reused. rework records:\n\n- new uuidv7 job id;\n- incremented attempt/rework lineage;\n- `supersedesjobid`;\n- triggering conflict or decision reference.\n\n## concurrency\n\nclaims use optimistic concurrency on the agent state. mutating jobs use dedicated branches and leases. ambiguous mutation overlap is treated as a conflict. lease expiry produces `reconcile_required`; it never authorizes silent reassignment.\n\n## master status\n\nroutine status is built from compact registry and status indices. master resolves detailed jobs, responses, reviews or provider mutations only through exact pointers when status is stale, contradictory, materially risky or explicitly requested.\n\nthe human can ask master which agents need `go`, what is running, what is blocked, which reviews remain open and whether all expected responses arrived without inspecting raw json.\n\n# safor canonical agent job contract\n\nsafor v0.14 defines every master-to-agent job as an immutable, self-describing execution contract.\n\n## authoritative artifacts\n\n```text\nagents/{agentid}/inbox/{jobid}.json   authoritative machine contract\nagents/{agentid}/inbox/{jobid}.md     derived human-readable projection\nmaster/jobs/{jobid}.json              authoritative lifecycle\n```\n\nthe markdown projection may never override or expand the json contract. master writes and reads back both job artifacts before publishing the job as `waiting_human_go`.\n\n## required contract areas\n\n1. **identity** — uuidv7 job identity, git-safe key, type, contract revision and immutability.\n2. **lineage** — project, value stream, package, work item, sequence, attempt, rework, predecessor and conflict references.\n3. **provenance** — creation/issue timestamps and exact master version, run and state revision.\n4. **assignment** — target agent id, display name, identity revision, immutable identity pointer and reason.\n5. **domain context** — creation type, domain, factory, operating model and compatibility decision.\n6. **role contract** — mission, responsibilities, prohibited substitutions and decision boundaries.\n7. **skills** — explicit versioned descriptions, execution instructions and immutable source pointers.\n8. **task** — objective, instruction, expected outcome, completion definition, scope, exclusions, assumptions and acceptance criteria.\n9. **dependencies and inputs** — accepted predecessors and immutable read-only source pointers.\n10. **authorization** — mandate, actual-rights requirement, separate work/control repository rights and explicit prohibitions.\n11. **workspace** — product repository, dedicated branch, immutable base commit, allowed paths, response workspace and conflict keys.\n12. **scheduling** — priority, dispatch revision, wave, leases and `human_go_required` claim policy.\n13. **product output contract** — required artifact types and exact product write target.\n14. **response contracts** — all five typed response templates, schemas, control-repository targets, response index and resolution schema.\n15. **communication contract** — minimal chat-output model and prohibition of human domain conversation.\n16. **verification contract** — evidence, independent review, acceptance and integration authority.\n17. **constraints** — stop/pause/stale/mismatch behavior and prohibitions against scope expansion, role switch, self-acceptance, master-state writes, automatic job switching and prompt transport.\n18. **human-readable projection** — immutable repository/ref/path/blob pointer.\n\n## activation semantics\n\npublication of a job does not activate a normal chat agent. the job enters:\n\n```text\nwaiting_human_go\n```\n\nthe human opens the already bound agent chat and types exactly `go`. the agent binds single-use go evidence to that job and dispatch revision before claiming.\n\na git push, scheduler, polling, automation or host event cannot replace this human action for a normal `chat_agent`.\n\n## permission semantics\n\na declared job permission is only an upper bound.\n\nan operation is executable only when:\n\n```text\njob allows\nand active mandate allows\nand safor policy allows\nand actual host/provider rights allow\n```\n\njson never creates credentials, provider capabilities or repository rights.\n\n## separate write targets\n\na mutating job normally has two independent targets:\n\n```text\nwork_repository\n  dedicated job branch\n  allowed product paths\n\ncontrol_repository\n  agent state\n  typed responses\n  response index\n  evidence and audit\n```\n\nproduct-write permission never grants response-write permission. response-write permission never grants product-write permission.\n\ndirect default-branch mutation, merge and deployment are forbidden unless a separate later authority explicitly performs those operations outside the agent job.\n\n## response contracts\n\nevery job binds all five response types:\n\n| type | purpose | blocking |\n|---|---|---:|\n| `job_result` | completed work, outputs, git trace, checks and open items | no; current execution ends as submitted |\n| `job_error` | technical failure and safe-state evidence | yes |\n| `clarification_request` | ambiguous, incomplete or contradictory job | yes |\n| `capability_mismatch` | role, skill, domain, technology or identity mismatch | yes |\n| `improvement_proposal` | advisory non-blocking improvement | no |\n\neach binding contains response type, exact immutable template pointer, schema pointer and deterministic write target.\n\na response cannot grant authority, change role, expand scope or alter the job. master records its resolution separately.\n\n## conflict fields\n\nblocking responses contain at least:\n\n```text\nconflictid\nconflicttype\nseverity\ndescription\nblockedstep\naffectedrefs\nsuggestedresolution\nstatus = open\nresponsetemplateversion\n```\n\nthe agent stops the affected execution before further product mutation.\n\n## lifecycle separation\n\n```text\nprepared\n→ waiting_human_go\n→ go_observed\n→ claimed\n→ running\n→ response_submitted\n→ verified\n→ accepted\n→ integrated\n```\n\nthese states are not interchangeable:\n\n- submission is the agent's claim;\n- verification checks binding, evidence and provider effects;\n- acceptance applies factory, review and governance criteria;\n- integration records the actual merge or equivalent adoption.\n\n## rework and supersession\n\na historical job id is never reused. rework or substantial changes produce a new uuidv7 job with:\n\n- incremented attempt/rework lineage;\n- `supersedesjobid`;\n- immutable conflict/decision reference;\n- fresh authority, input and branch snapshots.\n\n## independent review\n\nwhen independent review is required, the reviewer must differ from the contribution author. the reviewer receives a separate job with its own role, skills, inputs, branch/read scope and response contracts.\n\n## minimal chat output\n\nthe agent chat is not a result store. it may emit only `ready`, `started`, `submitted`, `blocked` or `reidentification_required`, each as one short line. detailed content belongs in git.\n\n# safor multi-agent scheduler\n\nsafor v0.14 provides a master-owned scheduler for safe parallel work across persistent agents.\n\n## boundary: scheduling is not chat activation\n\nthe scheduler may:\n\n- derive ready atomic work;\n- match roles, capabilities and actual provider rights;\n- reserve capacity and conflict domains;\n- create dedicated job branches;\n- materialize immutable jobs and inbox pointers;\n- publish a human start list.\n\nfor a normal `chat_agent`, the scheduler may **not** start the chat. the dispatch result is:\n\n```text\nwaiting_human_go\n```\n\nthe human deliberately types `go` in each bound agent chat. git push, polling, automation and host events do not replace this step.\n\n## scheduling formula\n\n```text\nparallel dispatch capacity\n= min(\n    free eligible agent slots,\n    ready atomic work,\n    project parallelism ceiling,\n    maximal conflict-free job set\n  )\n```\n\n## atomic work\n\na work item is either:\n\n- `composite` — planning/container work; never dispatched directly;\n- `atomic` — independently executable and assessable agent work.\n\nevery atomic work item declares:\n\n- dependencies and join predicate;\n- required capabilities;\n- immutable inputs;\n- product write conflict domains;\n- exclusive keys;\n- expected outputs;\n- acceptance and evidence requirements;\n- reviewer independence constraints;\n- priority and readiness metadata.\n\n## eligibility\n\nan agent is eligible only when:\n\n- identity status is `active`;\n- registry dispatch is enabled;\n- a normal chat identity has `bound` chat binding;\n- required role and capabilities match;\n- at least one scheduling slot is free;\n- separation of duties remains satisfiable;\n- actual provider rights cover the proposed job;\n- no reidentification requirement exists.\n\n## conflict model\n\nparallel execution is allowed only when:\n\n- dependencies are already accepted;\n- reads are pinned to immutable revisions;\n- write conflict domains do not overlap;\n- exclusive keys do not overlap;\n- dedicated branches are unique;\n- capacities are free;\n- mandates, rights and review constraints pass.\n\n`unknown` or `project_wide` mutation scope conflicts with all other mutating jobs. ambiguity is serialized.\n\nread-only jobs do not conflict solely because they inspect the same immutable input.\n\n## deterministic order\n\ncandidates are ordered by:\n\n1. priority descending;\n2. ready-since timestamp ascending;\n3. work-item id ascending;\n4. agent id ascending.\n\nthis makes equivalent scheduling inputs replayable.\n\n## dispatch waves\n\nmaster persists every decision in:\n\n```text\nmaster/dispatch-waves/{waveid}.json\n```\n\na wave records considered work, assignments, job pointers, branch names, acquired leases and the activation boundary:\n\n```text\nnormalchatagentsactivated = false\ndispatchoutcome = waiting_human_go\nhumangorequired = true\n```\n\n## resource leases\n\nbefore publication, master reserves:\n\n- agent slot;\n- write conflict domain;\n- exclusive key;\n- dedicated branch.\n\nlease states are:\n\n```text\nreserved\n→ active\n→ release_pending\n→ released\n```\n\nif expiry or external effects are uncertain:\n\n```text\nreconcile_required\n```\n\nexpiry never authorizes silent reassignment. master must first prove
